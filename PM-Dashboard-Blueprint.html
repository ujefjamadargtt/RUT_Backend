1.2 Project Manager terminology — read carefully, three things look alike but aren't

  • Project Manager is a role (rank 6) — the renamed "Service PO Admin." It has no attachment to any specific project record.
  • Delivery Head is not a role — it's a per-Service-PO staffing field (service_pos.delivery_head_employee_id), an FK to Employee. It answers "who delivers this PO," independent of anyone's role.
  • Account Manager (service_pos.account_manager) is a plain free-text string, not a foreign key — not queryable, not an employee reference at all.

No column anywhere marks an employee as "the Project Manager of this Project." See §9 for what this means for dashboard scoping. Business rule needs confirmation

1.3 Existing dashboards

One dashboard module exists (src/routes/dashboard.routes.js), company/BU-wide, gated only by generic authentication — no role or capability check anywhere in this file. It has two halves:

  • Core stats + breakdowns: /dashboard/stats (workforce, portfolio, current-month hours, financials, monthly-hours trend, top POs by hours), plus employee-billable-breakdown, po-billable-breakdown, top-employees-by-po, billable-trend.
  • Analytics: /dashboard/analytics (fiscal-year/quarter drill: hours by client/employee, client × Service PO matrix, bench %) and /dashboard/analytics2 (10 bundled reports: monthly resource utilization, cost trend, client-wise cost, top clients by cost, leave-hours trend, no-work trend, per-project cost breakdown, budget vs billed).

None of it is scoped to "my team" or "my projects" — every figure is company- or BU-wide. Verified

1.4 Existing reports

Three distinct report layers exist, each with its own character:

  • Reports module (report.routes.js, 23 endpoints) — cost/hours/utilization/client breakdowns, BU-wide.
  • Management Reports (managementReport.routes.js, 10 endpoints) — a newer, purpose-built layer over cost_budget_master/resource_budget_master: profitability, margin forecast, staffing-plan accuracy, client concentration, BU scorecard, capacity forecast, PO timeline risk, delivery-head performance, invoice realization, service-line mix. This is the single most PM-relevant, least-surfaced part of the codebase — see §2.
  • Employee self-service reports (employeeReport.routes.js) — an employee's own daily/monthly/range hours, plus two reports that already resolve a "my team" scope: timesheet-approval-status and work-log-time.
  • Work-log compliance report (employeeWorkLogCompliance.routes.js) — a dedicated missing/short-hours list, already correctly team-scoped for a Project Manager (see §9).

1.5 Project-related screens

CRUD for Client → Project → Service PO → Service PO Hierarchy (parent/child nodes), plus four budget/cost modules hanging off Service PO: ServicePOMonthlyBudget, CostBudget, ResourceBudget, MonthlyCost. Screen usage inferred from route naming; no frontend in this repo to confirm.

1.6 Employee / team-related screens

  • Employee Master — full CRUD, the richest employee-visibility endpoint (see §9, Algorithm A).
  • Team Mapping ("My Team") — a Project Manager's own roster of Team Leads, plus which Service POs each Team Lead may operate on.
  • Manager Self-Service ("My Team") — a manager's own employees, monthly work log on their behalf, and the timesheet approval queue.
  • Employee Service PO Mapping — admin-side assignment of employees to Service POs (a plain link, see §1.8).

1.7 Work log / timesheet functionality

A genuine two-stage pipeline:

  1. Draft — employee_work_logs, entered via Daily Timesheet (time-slot or single-hours entry, mutually exclusive) or Monthly Work Log (whole-month replace-save, 176h cap). Carries the approval state (§9).
  2. Official — timesheets, populated only by an explicit "Sync Employee Work Logs → Confirm Import" action that flips the source rows to synced inside one transaction. timesheets itself has no approval-status field — only a one-way is_publish flag.

1.8 Task / work allocation

EmployeeServicePOMapping is a pure binary link (employee ↔ Service PO, active/inactive) — no allocation percentage, no planned hours. Planned hours live in a separate table, ResourceBudget (employee × Service PO × month → hours), capped app-side at 176h/employee/month across every PO. Nothing joined these two concepts together until the new Resource Staffing Plan Accuracy management report (§2) — the first place planned vs. actual hours are actually compared. Verified

1.9 Project allocation / mapping

Three link tables, each a distinct relationship — don't conflate them: TeamMapping (Project Manager ↔ their Team Leads), ManagerServicePOMapping (a Team Lead's grant to operate on a specific Service PO), EmployeeServicePOMapping (an employee's staffing on a Service PO). None carry a percentage or planned-hours figure themselves.

1.10 Project status

Project.status is minimal: only active / inactive — no on-hold, delayed, or completed value exists at Project grain. ServicePO.status is the real lifecycle field: in-progress, completed, on-hold, pending, cancelled, closed. No progress %, completion %, or milestone concept exists anywhere in the schema — confirmed by reading every model in the chain. Verified — do not assume otherwise

1.11 Utilization / availability

Utilization is well covered: resource-utilization, monthly-resource-utilization, employee-capacity-forecast (176h-cap based), resource-staffing-plan-accuracy, plus employee_bench_pct on the dashboard. Availability, in the leave/absence sense, does not exist — see §1.12.

1.12 Leave / absence

Confirmed absent

No leave, absence, vacation, or availability model exists anywhere in this codebase. The only related artifacts are label heuristics — a "leave hours trend" chart and a bench % figure both work by string-matching Service Types literally named "Leave"/"Leaves"/"Bench"/"Idle," not by reading a structured leave record. Any "who's on leave" widget would need new schema, not a new endpoint.

1.13 Billing / non-billing

ServicePO.is_billable is a first-class boolean, derived from Service Type → Service Category (report_bucket_key = 'billable') and re-derived on every import regardless of what a spreadsheet says. Already used by several dashboard/report breakdowns. Verified

1.15 Notifications / alerts

The Notification model has a complete read API (list, mark-read, mark-all-read, delete) — but zero producers write to it anywhere in the codebase. What exists instead are two manual, click-to-send reminder emails (APPROVAL_REMINDER, employee-triggered; WORKLOG_COMPLIANCE_REMINDER, viewer-triggered from the compliance report) and a separate AI Insights module — 10 LLM-generated insight types (including bench_escalation, sole_contributor_risk, po_ending_alerts, timesheet_compliance) each with a severity, summary, and audience_roles array. Whether "Project Manager" is seeded into any insight's audience_roles was not verified — confirm before relying on it.

1.16 Existing charts / cards / tables

The codebase already produces: trend line series (monthly hours, billable %, cost), stacked/grouped breakdown tables (per-employee, per-PO, per-client), a bench-% figure, pivot-style utilization tables, and page-level summary totals on most paginated reports. Several "paginated" reports (client-wise-analytics, employee-bench-percentage, budget-vs-billed, resource-utilization-trend, service-po-hours-budget) actually pull the full filtered set into Node and slice it there rather than using SQL LIMIT — worth knowing before assuming any of them scale past a few hundred rows.

Active Projects/POs · Team Headcount · Missing Work Logs · Pending Approvals · Overallocated Employees · Logged Hours (MTD) · At-Risk Projects · Budget vs. Billed Variance · Bench % · Utilization %. Trimmed to a final 5–8 in §11.

Work Log section

Compliance list, submitted vs. missing counts, expected vs. logged hours, employee-wise exceptions.

09 / 14

Role and data visibility

This is the section to read most carefully before building anything — several scoping mechanisms coexist and disagree with each other.

9.1 Project / Client scope: BU-wide, no ownership field

There is no field on Project or Client identifying an owning Project Manager. A Project Manager's visibility is resolved purely by Business Unit membership — resolveReportCompanyScope falls back to every BU the PM is mapped to when no X-Company-Id header is sent. Two Project Managers mapped to the same BU see identical Client/Project lists — there is no per-record "mine" concept. src/services/companyAccessControlService.js:450-521 · src/middlewares/resolveReportCompanyScope.js

9.2 Service PO scope: a real exception

Unlike Project/Client, servicePOService.getAll/getById applies an additional narrowing specifically for Project Manager and Delivery Head — restricting them to individually-mapped Service POs rather than every PO in the BU. src/services/servicePOService.js:147-241

Business rule needs confirmation

Project/Client visibility is BU-wide while Service PO visibility is individually scoped for the same role. Should Project/Client follow the same individual-scoping model for consistency, or is BU-wide correct for those two and PO-level scoping the deliberate exception? This decision changes what "my projects" even means for the dashboard.

9.3 Two incompatible "my team" algorithms

This is the most consequential finding in the audit. Two different functions answer "which employees does this Project Manager manage," and they disagree:

Practical consequence

HR normally sets an employee's PRIMARY manager to their immediate Team Lead, not the Project Manager two levels up — so a normally-configured Project Manager has no direct mapping row at all. That PM sees their full team correctly on Employee Master and the Compliance report (Algorithm A), but sees zero employees on every approval-related screen (Algorithm B). Any dashboard tile built by calling the approval endpoints directly will show an empty/near-zero count for a properly configured Project Manager.

Business rule needs confirmation

Should the approval-side resolver (Algorithm B) be extended to also walk team_mappings, matching Algorithm A? This is a real code change if the dashboard needs a working "pending approvals" count for Project Managers — it is not a reporting nuance that can be designed around.

9.4 Team Mapping module: single-BU only

Unlike Project/Client/Service PO reads, the Team Mapping ("My Team") module was not given the multi-BU role-reach treatment — a Project Manager mapped to more than one BU sees only one BU's team at a time, selected via header. Needs confirmation if a multi-BU PM should see one combined roster.

9.5 A third, independent scoping rule for budgets

ServicePOMonthlyBudget's allowed-PO scope restricts Team Lead to mapped POs, but leaves every other role — Project Manager included — unrestricted beyond BU scope. A third scoping rule, inconsistent with both 9.1 and 9.2. src/services/servicePOMonthlyBudgetService.js:78-95

9.6 The recurring PRIMARY-manager gap

An employee lacking a PRIMARY manager_employee_mappings row has work logs that stay stuck at pending indefinitely — this is unchanged by anything on this branch and will silently understate a PM's "pending approvals" count regardless of which algorithm above is used.

9.7 No availability/leave scope to speak of

Reiterating §1.12: there is no data to scope, because there is no leave/absence model at all.

Working recommendation

Until product confirms otherwise, build the dashboard's team-facing widgets against Algorithm A's logic (the one Employee Master and the Compliance report already use) rather than the approval module's narrower resolver — it is the more complete of the two and is already proven correct for a Project Manager. This is a recommendation, not something implemented here.

Conclusions

1. How much can be built from existing APIs?

Roughly 65–70% of the final dashboard in §11 reuses existing service logic directly — every utilization, compliance, budget, and billable metric already has a working endpoint. The remaining ~30–35% is concentrated in three things: rolling Service-PO data up to Project grain (nothing does this today), reconciling the two conflicting "my team" scope algorithms (§9.3), and synthesizing a single risk/exception view from three separate reports. None of that missing 30% requires new raw data collection — it's aggregation and scope-consistency work, not new schema, except where §9's ownership question is answered in favor of a literal per-project field.

2. Most valuable existing APIs

resource-staffing-plan-accuracy, employee-work-log-compliance, employee-capacity-forecast, service-po-timeline-risk, dashboard/stats, monthly-resource-utilization, budget-vs-billed, timesheet-approval-status/work-log-time (once the scope gap is fixed), service-po-summary.

3. Which existing APIs are missing important PM metrics?

None roll up to Project grain. None give a consistent "my team" scope across approval-related endpoints. None express project ownership, task/milestone completion, or leave/availability — because none of that data exists yet.

4. Which new APIs should be created?

Three, in order: the Project-level rollup, the "my team" scope fix for approvals, and the risk/exception synthesis endpoint. Everything else in §13 is lower priority or explicitly contingent on a business decision.

5. What should NOT be shown on the PM dashboard?

  • All-time, unfiltered client-cost views (they exist only as such — no period filter reaches them)
  • Raw hour-by-hour timesheet detail — that belongs on the existing Reports module, not a dashboard tile
  • The Entity-Admin-only BU performance scorecard
  • Employee self-service daily/monthly calendars — those are personal, not PM-facing
  • A duplicate of any existing report in full — the dashboard summarizes, it doesn't replace drill-through reports

6. Top 10 PM metrics, ranked

  1. Missing work logs
  2. Pending approvals
  3. At-risk / overdue projects
  4. Overallocated employees
  5. Team headcount
  6. Logged hours (MTD)
  7. Underutilized / bench employees
  8. Planned-vs-actual hours variance
  9. Budget vs. billed variance
  10. Project / PO status distribution

7. What should the PM see immediately after opening the dashboard?

The KPI row and the Action Required section, both already populated for the current month and the PM's full BU-reach scope — no filter interaction required to see something useful. The Project table loads sorted by risk, not alphabetically. The first screen should read as "here is what needs your attention today," not a blank filter form waiting for input.
